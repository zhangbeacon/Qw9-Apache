# 赛题一项目说明（给队友）

> 第九届“强网”拟态防御国际精英挑战赛 · 设计安全大赛
> 赛题：面向软件多样性的异构变体构造与安全增益验证
> 整理：2026-10-27

## 0. 一分钟版

**一句话目标：**

选一个开源程序 V1，自动生成两个功能一致、内部不同的版本 V2/V3，再用至少 3 个不同根因的 CVE 打这三个版本，证明它们的**安全相关表现不一样**。

**三个硬性要求：**

1. 至少 3 个漏洞，根因不同；
2. V1/V2/V3 功能一致；
3. 差异必须能外部观察、可复核，不能只是哈希/地址不同。

**两个阶段：**

- 第一阶段（现在–11.6）：交设计理念，报告/论文/伪代码，筛选轮；
- 第二阶段（11.9–11.27）：交完整源码、详细设计，部分题目要上环境验证；
- 线下答辩（12.6）：最终获奖队伍。

**现在最该做的：**

定基准程序 + 找 3 个 CVE 候选，不是先写文档。

---

## 1. 比赛到底要什么

不是让你造一个“打不穿”的系统，而是让你证明：

> 同一个攻击脚本，在 V1 上能成功，在 V2/V3 上**表现不一样**。

“表现不一样”包括：

- V1 触发，V2/V3 不触发；
- V1/V2 触发，V3 不触发；
- 三个都触发，但利用原语、控制流、泄露程度或最终目标不同；
- 某个版本能检测、隔离或拦截，其他不能。

**不算差异：**

- 只有文件哈希、代码大小、地址、指令排列不同；
- 只有时间戳、签名、调试信息、压缩形式不同；
- 正常随机性造成的输出差异（除非能证明它和攻击相关）。

---

## 2. “安全增益”的正确理解

错误说法：

> “我们的变体抗住了 CVE 攻击。”

正确说法：

> “同一漏洞在 V1 上成功触发，在 V2/V3 上表现为 [未触发 / 利用原语失效 / 攻击链中断 / 泄露减少]；漏洞本身 [仍存在但利用受抑制 / 已消除]，依据是 [具体证据]。”

赛题明确要求区分两类结论：

- 漏洞仍存在，但利用受抑制；
- 漏洞已消除。

不能拿有限测试宣称“绝对安全”。

---

## 3. 总体流程（五步）

1. **选程序**：Linux x86-64、可复现构建、至少 3 个不同根因的 CVE；
2. **固化 V1 + 漏洞基线**：在 V1 上稳定复现 3 个 CVE；
3. **设计变换**：针对“攻击依赖什么”来变；
4. **生成 V2/V3**：自动化流水线、功能一致、记录种子和参数；
5. **三版本对比**：同一脚本打三个版本，形成反应矩阵。

顺序不能反：**先有漏洞基线，再设计变换**。否则流水线做出来，差异和漏洞无关。

---

## 4. 怎么选基准程序

三个条件，缺一不可：

1. Linux x86-64 能构建、能运行；
2. 有明确的功能接口（文件解析、网络协议、命令行都行）；
3. 同一版本至少有 3 个**不同根因**、可复现的 CVE。

评分表（团队一起打分）：

| 维度 | 权重 | 说明 |
|---|---|---|
| 构建难度 | 20 | 依赖少、构建快、能容器化 |
| CVE 数量与独立性 | 30 | 3 个以上，根因不同，有补丁/公告 |
| 复现难度 | 25 | 有 PoC、触发条件明确、能本地跑 |
| 代表性与攻击面 | 15 | 真实软件、有外部输入/网络接口 |
| 许可证与依赖 | 10 | 能提交、能修改、能分发 |

候选方向（需逐个核实）：

- 文件解析：libxml2、libtiff、libpng；
- 网络服务：nginx、dnsmasq；
- 协议/工具：openssl、sqlite。

不要选“为了展示漏洞临时写的单功能样例”，实用性和泛化能力会被扣分。

CVE 调研模板：

| CVE | 影响版本 | 根因 | 触发条件 | 补丁 | PoC/复现 |
|---|---|---|---|---|---|
| | | | | | |

## 5. 流水线长什么样

最小版本：

```text
输入 V1 源码 + 配置
  → 分析（可选）
  → 变换（一种策略）
  → 构建
  → 打包
  → 日志（工具版本、参数、种子、产物哈希）
  → V2 / V3
```

必须记录：

- 工具版本（编译器、LLVM、链接器、依赖）；
- 变换参数；
- 随机种子；
- 构建日志；
- 产物标识（哈希）。

加分项：

- 多种变换组合；
- 配置化/插件化，能换程序；
- 容器镜像；
- 一键重跑；
- 同一变体两次构建哈希一致。

## 6. 漏洞验证怎么做

每个漏洞准备一张卡：

| 字段 | 内容 |
|---|---|
| 编号 | VULN-01 |
| CVE/CWE | CVE-XXXX-XXXX / CWE-XXX |
| 影响版本 | |
| 根因 | |
| 影响位置 | 文件/函数/行 |
| 触发条件 | |
| 攻击目标 | 崩溃/泄露/执行命令/绕过认证 |
| 判定依据 | 退出码/ASan/日志/协议响应/探针 |
| V1 结果 | |
| V2 结果 | |
| V3 结果 | |
| 结论 | 未触发/触发但表现不同/触发且一致 |

同一脚本打三个版本，结果矩阵：

| 漏洞 | V1 | V2 | V3 | 差异判定 |
|---|---|---|---|---|
| VULN-01 | 触发 | 未触发 | 未触发 | 有效 |
| VULN-02 | 触发 | 触发但无控制 | 触发 | 有效 |
| VULN-03 | 触发 | 触发 | 触发 | 无效，需调整 |

注意：

- 同一根因多个输入只算 1 个漏洞；
- 判定规则要能复核，探针要能解释“为什么算差异”；
- 控制正常误报：固定环境、固定种子、多次重复。

## 9. 第一阶段文档写什么

评委想看四件事：

1. 你懂不懂题；
2. 基准程序和漏洞靠不靠谱；
3. 方法新不新、能不能自动化；
4. 第二阶段做不做得出来。

建议目录：

1. 作品简介与团队
2. 问题理解：单一实现的共因失效
3. 威胁模型
4. 基准程序选择（主选+备选，3 个 CVE 候选）
5. 总体方案：流水线架构
6. 核心变换方法（原理+伪代码）
7. 变体差异与功能一致性
8. 漏洞验证与安全增益判定
9. 创新点与对比
10. 可行性与 Stage 2 计划

不用写完整实现，但要有：

- 架构图；
- 核心伪代码；
- CVE 表（编号、版本、根因、补丁）；
- 预期结果矩阵；
- 一个小实验更好（哪怕只跑通一个漏洞）。

## 10. 常见坑

1. 把“二进制不同”当“有效异构”；
2. 把“混淆”当“修复”；
3. 先搭流水线后找漏洞 → 差异和漏洞无关；
4. 三个输入同一个根因 → 只算 1 个漏洞；
5. 功能测试没有判定规则 → 不知道输出不同是正常还是异常；
6. 不记录种子/版本 → 评审无法复现；
7. 性能只测一个负载；
8. 宣称“绝对安全”。
