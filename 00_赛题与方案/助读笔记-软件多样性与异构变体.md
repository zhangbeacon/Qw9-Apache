# 赛题助读笔记：从软件多样性到安全增益验证

> 适用赛题：面向软件多样性的异构变体构造与安全增益验证
> 整理时间：2026-10-27

## 0. 这份笔记怎么用

推荐顺序：

1. 先读第 1 章，搞懂“为什么需要多个版本”；
2. 再读第 2 章，搞懂“怎么造 V2/V3”；
3. 然后读第 3 章，搞懂“怎么证明差异有效”；

5. 第 5 章是把所有东西拼成项目的落地建议。

每篇都按“定位 → 核心 → 对项目的用处 → 局限”写。标了“摘要级”的，是我只核实了摘要或开头，具体细节要以原文为准。

## 1. 概念地基：为什么需要多个版本

### 1.1 《什么是软件多样性？》

原文：[https://baeldung.cn/cs/software-diversity](https://baeldung.cn/cs/software-diversity)

**定位**：入门科普，建立直觉。

**核心**：

- 单一实现的风险：一个用户失败，所有同条件用户可能一起失败；一个利用，可能影响所有用户。
- 软件多样性：不同实现解决同一问题，满足相同需求，给出相同正确结果。
- 四种来源：多供应商、多编译器、随机性、自然多样性。
- 两类收益：安全（漏洞/后门不会完全传播）、容错（一个错误不会拖垮整个系统）。

**对项目的用处**：

- 写“选题动机/背景”时的通俗论据。
- 帮你们向队友解释“为什么不能只交一个版本”。

**局限**：

- 只是概念，没有构建、测试、判定方法。
- “相同输入→相同输出”是理想化说法，真实程序有随机性、时间戳等差异。

---

### 1.2 《拟态防御 Web 服务器设计与实现》

原文：[https://www.jos.org.cn/html/2017/4/5192.htm](https://www.jos.org.cn/html/2017/4/5192.htm)

**定位**：DHR 结构的经典中文论文，解释“多个变体怎么协同”。

**核心**：

- 系统 = 输入代理 + 异构执行体集 + 表决器 + 动态选择。
- 同一输入复制 n 份，n 个执行体分别处理，表决器取“相对正确”的输出。
- 三个支柱：
  - 异构性：防同一漏洞同时在多个执行体生效；
  - 冗余性：多执行体同一请求，多数表决兜底；
  - 动态性：被突破后换执行体，让攻击难以维持。
- 2 个执行体结果不一致时无法裁决；3 个是最小多数表决。
- “同源”问题：表面异构、实质同框架，防不住共同漏洞。
- 攻击针对非异构属性时，DHR 失效。

**对项目的用处**：

- 解释“为什么是 V1+V2+V3 三个版本”，而不是两个或五个。
- 解释“有效差异”的判据：差异要落在攻击依赖的属性上。
- 表决层次（集中/分布、语义/数据）可以启发你们的差异判定规则。
- 引用它的边界，让报告结论更可信。

**局限**：

- 2017 年 Web 服务器原型，测试集有限。
- “相对正确”不是“绝对正确”；共生漏洞、多数被攻破时表决失效。
- 赛题不要求实现完整 DHR 运行时。

### 1.3 《N-Variant Systems》（USENIX 2006）

原文：[https://www.usenix.org/legacy/event/sec06/tech/full_papers/cox/cox_html/](https://www.usenix.org/legacy/event/sec06/tech/full_papers/cox/cox_html/)

**定位**：多变体执行的经典英文论文，讲“不靠秘密的多样性防御”。

**核心**：

- 同一输入送给多个自动多样化变体，监控器观察行为分歧。
- 变体在正常输入上保持客户端可见行为一致，在异常/攻击输入上产生分歧。
- 例子：两个变体使用不相交的内存空间，绝对地址攻击必然在其中一个变体上非法。
- 攻击者必须用同一输入同时攻破所有变体，才算成功。
- 不依赖随机化秘密，因此不怕秘密泄露。

**对项目的用处**：

- 理解“为什么多个变体比单个变体难打”。
- 学习“正常等价 + 分歧检测”的表述方式，写报告时可以直接借用。
- 为“同一脚本打三个版本、观察差异”提供理论依据。

**局限**：

- 2006 年的原型，假设程序行为确定性；真实程序有非确定性。
- 只讲检测/阻断，不讲恢复；性能开销和兼容性是现实问题。
- 不是竞赛评分规则，不能直接套用。

## 2. 怎么造变体

### 2.1 《基于 LLVM 的多样化编译方法》

原文：[https://www.sciengine.com/ComputerEng/doi/10.19678/j.issn.1000-3428.0068314](https://www.sciengine.com/ComputerEng/doi/10.19678/j.issn.1000-3428.0068314)

**定位**：最贴近赛题“变体构造流水线”的中文论文。

**核心**：

- 现有工具对整份文件用同一种变换，差异单一。
- 新方法：代码感知 + 分组混淆 + 函数级随机选择。
- 流水线五步：输入 → 代码感知 → 裁决 → 方案库 → 输出。
- FPRA 算法：按概率决定是否变换，按函数特征选组，组内随机选方案，变完检查保护指标。
- 安全测试：10 个 CTF 堆/栈溢出案例，对比 gadget 和控制流图。
- 性能测试：OpenSSL、Nginx、SPEC CPU 2017。

**对项目的用处**：

- 流水线骨架可以直接借鉴，但要补构建、打包、部署、日志。
- V2/V3 可以用“不同种子 + 不同策略组”生成。
- 差异量化可以借它的指标：gadget、控制流图、文件大小、运行时间。
- 性能测试方法可以借：多负载、多轮、取平均。

**局限**：

- 混淆不等于修复漏洞；源代码逻辑漏洞可能三个版本都有。
- 安全测试是 CTF 案例，不是真实 CVE；代表性有限。
- 摘要说“几乎无影响”，正文 RSA 校验只有 64%；别照抄摘要。
- 依赖 LLVM 15，换版本可能不兼容。

## 3. 怎么证明差异有效

### 3.1 《拟态构造的 Web 服务器异构性量化方法》

原文：[https://www.jos.org.cn/html/2020/2/5615.htm](https://www.jos.org.cn/html/2020/2/5615.htm)

**定位**：回答“几个变体到底有多不一样”。

**核心（摘要级）**：

- 把异构性定义为执行体集的“复杂性 + 差异性”。
- 借鉴生物多样性量化方法，提出适合拟态构造的量化指标。
- 讨论冗余度、构件、执行体的选择。
- 指出异构性高不等于没有共同漏洞。

**对项目的用处**：

- 报告里“差异来源/变换层次”的量化可以借它的思路。
- 帮你们解释“为什么选这三个变体，而不是随便三个”。
- 提醒你们：异构性得分高，不等于安全增益大。

**局限**：

- 指标依赖特征/漏洞数据和假设；未知共性缺陷无法穷举。
- 论文场景是 Web 服务器，不是通用程序。
- 我只核实了摘要和开头，具体公式要以原文为准。

---

### 3.2 《多变体执行误报问题分析与解决方法综述》

原文：[https://di4s.chinaxiv.org/abs/202205.00138v1?locale=zh_CN](https://di4s.chinaxiv.org/abs/202205.00138v1?locale=zh_CN)

**定位**：回答“三个版本结果不一样，就一定是被攻击了吗”。

**核心（摘要级）**：

- MVX 的共性问题是误报：正常运行时也会产生非一致变量，如内存描述符、端口号、随机数、线程调用顺序。
- 归纳三类解决策略：Pina 算法同步、编译器模块插桩、缩小表决边界。
- 比较各策略的功能、性能和优缺点。
- 指出未解决的难点和未来方向。

**对项目的用处**：

- 设计判定规则时，先区分“正常差异”和“攻击差异”。
- 固定随机种子、控制环境、隔离变量，降低误报。
- 报告里要写“误报控制”，这是实验严谨性的一部分。

**局限**：

- 聚焦误报/同步/裁决，不是变体生成教程。
- 策略有适用场景，不能无脑套用。
- 我只核实了摘要，具体实验数据要以原文为准。

### 3.3 《基于跨版本测试的编译器引入型漏洞检测方法》

原文：[https://crad.ict.ac.cn/article/doi/10.7544/issn1000-1239.202550226](https://crad.ict.ac.cn/article/doi/10.7544/issn1000-1239.202550226)

**定位**：差分测试在“编译器版本差异”上的应用。

**核心（摘要级）**：

- 编译器可能在编译过程中引入安全漏洞。
- 方法：基于通用安全代码建模 + 差分测试，定位安全代码是否被优化掉。
- 通过错误处理函数识别安全代码，比较不同版本中安全检查的差异。
- 在 Linux 内核上评估，漏报率低、误报率可接受。

**对项目的用处**：

- 借鉴“跨版本对比 + 差分测试”的思路：同一输入，不同构建，比较安全行为。
- 提醒你们：编译器/优化本身也可能改变安全行为，这既是风险也是多样化机会。
- 为“为什么换编译器/优化级别可能影响漏洞”提供依据。

**局限**：

- 目标是检测编译器引入的漏洞，不是通用漏洞复现方法。
- 依赖静态分析和安全代码建模，门槛较高。
- 我只核实了摘要，具体方法细节要以原文为准。

## 4. 怎么观察漏洞、怎么复现

### 4.1 《Address Sanitizer 基本原理介绍及案例分析》

原文：[https://cloud.tencent.com/developer/article/2206844](https://cloud.tencent.com/developer/article/2206844)

**定位**：内存类漏洞的观察工具入门。

**核心**：

- ASan 在 malloc/free 前后插“毒区”（redzone），编译器在每次内存访问前插检查。
- 能检测：use-after-free、heap/stack/global buffer overflow、use-after-return、memory leak 等。
- 报告会给出错误类型、出错地址、分配/释放栈，便于定位。
- 有性能和内存开销，通常用于测试/调试。

**对项目的用处**：

- 复现内存漏洞时，用 ASan 观察“到底哪里越界/释放后使用”。
- 作为漏洞测试包的判定依据之一：同一输入在 V1 上 ASan 报错，V2/V3 不报错或报错不同。
- 报告里可以贴 ASan 输出作为原始证据。

**局限**：

- 只能检测访问到“毒区”的情况；越界到另一个合法分配里可能漏报。
- 有开销，可能改变时序，影响并发类漏洞。
- 不报错不等于漏洞不存在。

### 4.2 《可重复构建为软件供应链安全保驾护航》

原文：[https://www.openeuler.org/zh/blog/20230303-kechongfu/20230303-kechongfu.html](https://www.openeuler.org/zh/blog/20230303-kechongfu/20230303-kechongfu.html)

**定位**：交付/复现的基础设施知识。

**核心**：

- 可重复构建：相同源码、构建环境、构建指令 → 逐比特相同的制品。
- 差异来源：时间戳、随机数、文件顺序、构建路径、工具版本。
- 常用手段：libfaketime、SOURCE_DATE_EPOCH、确定性构建系统、解包对比/diffoscope。
- 目的：验证二进制没被植入后门，让构建过程可追溯。

**对项目的用处**：

- 赛题要求评审能按文档重新构建；你们要记录工具版本、参数、种子、日志、产物 ID。
- 注意区分：**同一个变体**要能重建出相同结果；**不同变体**本来就应该不同。
- 可以用“两次构建同一变体，比对哈希”来证明流水线可复现。

**局限**：

- 可重复构建不保证安全，只保证“可验证”。
- 完全确定性很难，尤其是并发、时间、随机数、文件系统顺序。
- openEuler 的方案是 RPM 场景，你们要按自己的构建系统调整。

## 5. 拼成你们的项目

### 5.2 建议的落地路线

**阶段 0：选基准程序**

- Linux x86-64、可复现构建、有明确功能接口；
- 至少 3 个可复现、根因不同的漏洞；
- 优先选有网络接口/外部输入处理的真实程序；
- 记录来源、版本、许可证、依赖、已知限制。

**阶段 1：最小流水线**

- 输入 V1 源码 + 配置；
- 一个变换策略（先别追求复杂）；
- 生成 V2、V3；
- 记录工具版本、参数、种子、构建日志、产物哈希；
- 能一键重跑。

**阶段 2：功能一致性**

- 正常输入、边界输入、异常输入；
- 定义“语义一致”的判定规则；
- 三版本对比，输出统一格式结果；
- 处理时间戳/随机数等正常差异。

**阶段 3：漏洞测试包**

- 至少 3 个不同根因的漏洞；
- 每个漏洞：根因、CVE/CWE、触发条件、攻击目标、影响；
- 同一脚本打 V1/V2/V3；
- 探针/判定程序；
- 结果矩阵：未触发/触发但表现不同/触发且一致。

**阶段 4：差异量化与性能**

- 差异来源、变换层次；
- 构建时间、运行时间、内存/体积；
- 多负载、多轮、取平均；
- 误报率、成功率。

**阶段 5：泛化与文档**

- 迁移到第二个程序/版本；
- 容器镜像/一键部署；
- 设计文档、测试报告、演示视频；
- 明确安全边界和结论适用范围。

### 5.3 还缺的资料/能力

- **基准程序选型**：需要实际调研哪些开源程序同一版本有 3 个以上独立 CVE，且有复现条件。
- **漏洞复现**：CVE 公告、补丁 diff、PoC、调试器/ASan 使用。
- **差分测试设计**：输入生成、判定规则、误报控制。
- **容器化/CI**：Docker、构建缓存、版本固定。
- **统计方法**：多次重复、成功率、异常样本分析。
- **安全边界**：无害化载荷、隔离环境、数据回收。

### 5.4 常见坑

1. 把“二进制不同”当“有效异构”——赛题明确不计分。
2. 把“混淆”当“修复”——漏洞可能还在，只是利用变了。
3. 功能测试只测正常路径——边界/异常输入才是漏洞温床。
4. 判定规则太粗（只看崩溃）或太细（噪声太多）——要平衡漏报/误报。
5. 不记录种子/版本——评审无法复现。
6. 同一根因多个输入重复计数——只算 1 个漏洞。
7. 性能只测一个负载——RSA 校验 64% 就是反例。
8. 结论外推——“测了 3 个漏洞”不等于“系统安全”。

---

## 6. 一页纸总结

- **为什么**：单一实现有共因失效风险；多个异构变体让同一攻击难以同时成功。（软件多样性、DHR、N-Variant）
- **怎么造**：LLVM pass / 编译选项 / 二进制重写；代码感知 + 分组变换；记录种子和版本。（LLVM 文章）
- **怎么验**：同一脚本打 V1/V2/V3；判定规则参考表决层次；控制误报；区分“漏洞仍在但被抑制”和“漏洞已消除”。（误报综述、异构性量化、跨版本测试）
- **怎么观察**：ASan 等工具；原始输出作为证据。（ASan）
- **怎么交付**：可重复构建、一键流水线、日志、测试包、结果矩阵、明确边界。（可重复构建）
- **比赛重点**：流水线 50 分 + 漏洞验证 30 分；差异必须安全相关，证据必须可复核。
