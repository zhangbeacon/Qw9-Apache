## 三、三个已复现 CVE 的交叉验证（PoC ↔ 修复 hunk）

**CVE-2021-41773**：修复 hunk 在 `ap_normalize_path()` 中新增对 `.%2e` 的识别——当路径段以 `.` 开头、后跟 `%2e`（且开启 unreserved 解码）时按 `..` 处理并回退 w。我们的 PoC `/icons/.%2e/.%2e/.%2e/.%2e/etc/passwd` 命中的正是这个分支：2.4.49 先判断 `..` 再解码，`.%2e` 逃过判断。**吻合**。

**CVE-2021-44790**：修复只有一行——`if (end - crlf <= 8) break;` 放在 `vlen = end - crlf - 8` 之前。我们的 PoC 用 `pad=3`（边界距 `\r\n\r\n` 不足 8 字节）与 `pad=0` 两档，前者使 `vlen` 下溢为 `SIZE_MAX`、后者触发巨量 `apr_pcalloc`。**吻合**。

**CVE-2021-44224**：修复引入 `AP_PROXY_WORKER_NO_UDS` 掩码，forward proxy（`PROXYREQ_PROXY`）不再对 `unix:` URI 做 `ap_proxy_de_socketfy()`，且 `fix_uds_filename()` 仅对非 forward 调用。我们的 A 变体（声明 UDS）与 B 变体（任意 UDS 回退）都依赖“forward 请求被当反代处理”这一缺陷。**吻合**。

→ 结论：静态挖掘出的修复点与本队动态复现的触发点**一一对应**，双向印证了根因判断。

## 四、八个待验证 CVE 的机制与触发假设

### 5. CVE-2022-22719 —— mod_lua `r:parsebody()` 读未初始化值（2.4.52→2.4.53）
**hunk 要点**：`lua_read_body()` 开头补 `*rbuf = NULL; *size = 0;`；读循环改为 `ap_get_client_block(r, *rbuf + rpos, length - rpos)` 的有界读；`ap_should_client_block()` 为假时返回 DONE。
**机制**：旧代码在无请求体/未读完时，`*size`（以及部分路径下的 `*rbuf`）保持未初始化 → Lua 脚本拿到随机长度/指针 → 读随机内存或崩溃。
**触发假设**：Lua handler 调 `r:parsebody()`，请求**不带 body**（如 GET）或 chunked body 中途异常；观察子进程崩溃/ASAN 报"use of uninitialized value"。
**难度**：中（需 mod_lua 配置，已有 44790 的 Lua 入口可复用）。

### 6. CVE-2022-22720 —— 请求走私（2.4.52→2.4.53）
**hunk 要点**：`ap_discard_request_body()` 出错分支统一 `goto cleanup`，`rc != OK` 时置 `c->keepalive = AP_CONN_CLOSE`；`end_output_stream()` 新增 status 参数，把错误桶写入响应。
**机制**：丢弃请求体遇到解析错误时，旧代码返回 400 但**不关闭连接**，剩余字节被当作下一个请求 → 走私。
**触发假设**：raw socket 发送 `Transfer-Encoding: chunked` 且 chunk 长度畸形/截断的请求，紧跟第二个请求；观察第二个请求被服务端当作独立请求处理。
**难度**：低（无需模块，纯 raw socket）。

### 7. CVE-2022-23943 —— mod_sed 堆越界写（2.4.52→2.4.53）
**hunk 要点**：`bufsize/size/remainbytes` 由 `int` 改 `apr_size_t`；`sed_write_output()` 中先判断 `sz >= ctx->bufsize` 再直接 `apr_pmemdup` 输出，失败路径 `clear_ctxpool`。
**机制**：旧代码用 `int` 承接输出尺寸，巨大输出时溢出为负 → `memcpy` 尺寸错误 → 堆越界写。
**触发假设**：启用 mod_sed（`OutputSed`/`InputSed`）且替换规则使输出远大于输入（如 `s/x/yyyy.../`），发送大 body 让输出逼近 2GB/INT_MAX。
**难度**：中高（需构造放大比与内存条件；ASAN 判定）。

### 8. CVE-2022-37436 —— 后端响应头截断（2.4.54→2.4.55）
**hunk 要点**：`ap_proxy_read_headers()` 返回值由 `void` 改 `apr_status_t`；`APR_STATUS_IS_ENOSPC` 时中止并清空 `headers_out`，调用方检查返回值。
**机制**：后端响应头超过 `ResponseFieldSize`（默认 8KB）时旧代码只告警并**继续用截断头**，后续头被并入 body；安全头（如 Set-Cookie）不被解释。
**触发假设**：自建恶意后端返回超长头行 + 带安全语义的后续头（Set-Cookie/X-Frame-Options），客户端在 body 中看到被并入的头。
**难度**：低（复用 44224 的后端设施）。

### 9. CVE-2023-25690 —— RewriteRule 回注请求走私（2.4.55→2.4.56）
**hunk 要点**：`mod_rewrite.c` 在 server/per-dir 两处新增 `ap_scan_vchar_obstext(r->args)` 检查，含控制字符/空格即 403；`mod_proxy_http.c` 转发前同样检查 `search`；新增 `RULEFLAG_QSNONE`。
**机制**：`RewriteRule "^/here/(.*)" "http://backend/elsewhere?$1" [P]` 把用户输入拼进查询串，`%0d%0a`/空格可拆分出第二个请求行 → 请求走私。
**触发假设**：按官方示例配置 RewriteRule+ProxyPass，请求 `GET /here/x%0d%0aGET%20/admin`，观察后端收到两个请求。
**难度**：中（需 mod_proxy + RewriteRule 配置）。

### 10. CVE-2023-27522 —— uwsgi 响应走私（2.4.55→2.4.56）
**hunk 要点**：状态行与头行增加长度检查、`ap_scan_http_token`/`ap_scan_http_field_content` 校验，非法即 502 并重置 `headers_out`。
**机制**：uwsgi 后端返回含控制字符的头/状态行，旧代码直接拼接转发 → 响应被截断/拆分。
**触发假设**：起一个 uwsgi 协议假后端，返回 `X-Foo: a\r\nInjected: b` 一类头，观察客户端响应被拆分。
**难度**：中（需写 uwsgi 协议后端，PoC 生态有现成脚本）。

### 11. CVE-2024-38474 —— mod_rewrite `%3f` 替换编码（2.4.59→2.4.60）
**hunk 要点**：新增 `RULEFLAG_UNSAFE_ALLOW3F`；替换结果中 `r->unparsed_uri` 含 `%3f` 且 `newuri` 含 `?` 时 403（除非显式 `UnsafeAllow3F`）；`prefix_stat` 与 `lastsub` 比较逻辑重写。
**机制**：请求 URI 中的编码问号 `%3f` 被解码进替换串，改变查询串边界，把 URL 映射到配置允许但不可达的目录/脚本 → 脚本执行或 CGI 源码泄露。
**触发假设**：配置带捕获组的 RewriteRule（映射到文件系统路径），请求路径含 `%3f`（或 `%253f`）触发解码后 `?` 出现。
**难度**：中高（需匹配的 RewriteRule 形态；官方 2.4.60 变更说明即触发条件）。

## 五、挖掘结论与下一步

1. **11/11 全部定位到修复文件与 hunk**；3 个已复现者与修复点完全吻合，**证明我们的复现不是"跑通公开 PoC"，而是能指到修复代码**——这正是文档里"根因证据"该有的样子。
2. **可立即推进的复现排序**（按难度）：
   - 低：22720（raw socket）、37436（复用后端）
   - 中：22719（复用 Lua 入口）、25690（RewriteRule 配置）、27522（uwsgi 假后端）
   - 中高：23943（mod_sed + ASAN）、38474（RewriteRule 形态）
3. **同根因提醒**：42013 是 41773 的同根因补丁绕过（**不计分**）；22719 与 44790 同在 `lua_request.c` 但缺陷不同（未初始化读 vs 下溢写），报告需并列展示两个修复 hunk 以证明根因独立。
4. **动态 fuzz（已启动，夜间运行）**：围绕 CVE-2021-44790 的真实触发结构做定向变异，已稳定命中 SIGSEGV/Abort，详情见第七节；23943/22719 的独立 fuzz 仍列为后续（需 libFuzzer/AFL++ 目标函数 `req_parsebody`/`sed_write_output`）。

## 七、定向模糊测试（夜间运行中）

**目标**：不看 PoC 的前提下，用定向变异独立撞出 `mod_lua` `r:parsebody()` 的崩溃（44790 边界距离条件）。

**触发条件（源码级精确定位）**：
`end = binstrstr(crlf, ..., boundary)`，`vlen = end - crlf - 8`；因此只有 **distance = end-crlf = 4 + pad ≤ 7（pad 0..3）** 才下溢。fuzz 构造按此设计：`--B CRLF headers CRLFCRLF + pad + B -- CRLF`。

**v3 暴露的问题**：检测每 20 发一次，保存的 body 未必是真正触发的那一发。逐发回放验证：
- 候选样本 **60 个** → **单发可复现 8 个**，其余 52 个为竞态误报（保存 body 与实际崩溃请求错位）。

**v4 改进**：逐发检测 + 命中后**单发回放验证**，只有回放仍崩才落盘为 `verified-*`；统计 `verified / false_positive`。

**边界窗口确定性实验**（pad 0..20 各 5 发，每发前确保服务器存活）：

| distance = 4+pad | 观察结果 |
|---|---|
| **4–7（pad 0–3）** | 出现 `SIGSEGV(11)` / `Abort(6)`（1–2/5；崩溃后重启与检测时序使计数偏低，但方向一致） |
| **≥8（pad ≥4）** | **0/5，无任何崩溃**（20–24 距离全零） |

结论：触发窗口与源码 `vlen = end - crlf - 8` 完全一致；8 个单发可复现样本已通过逐发回放验证并留档。

**当前状态**：v4 运行中（逐发验证，只保留可复现样本）；`fuzz/fuzz.log` 实时、`fuzz/summary.json` 收尾；实验结果见 `fuzz/boundary-experiment.json`。

**结论边界（如实）**：这是对**已知 CVE-2021-44790 的独立再发现**，证明方法能自己撞出缺陷，不等同于发现新漏洞；竞态误报已通过逐发回放剔除。

## 八、内存型 CVE 的另外两个：22719 / 23943 的定向尝试

**CVE-2022-22719（mod_lua 未初始化值）—— 已复现（Valgrind 判定）**
- 修复点：`lua_read_body()` 补 `*rbuf=NULL; *size=0;`（2.4.52→2.4.53）。
- **关键修正**：必须 `Content-Type: multipart/form-data; boundary=...` 且**无 body**（GET 或 CL:0）才会进入 `req_parsebody()` 的 multipart 分支；此前“无 Content-Type 的 GET”走 `ap_parse_form_data()` 安全分支，所以试不出——**本节此前“动态不可观测”的负结论作废**。
- 实测（Valgrind memcheck）：阳性阶段 2 次 `Use of uninitialised value of size 8 at strstr ← req_parsebody (lua_request.c:401)`，来源为 `req_parsebody` 栈帧 `lua_request.c:373` 的栈分配；阴性阶段（text/plain、无 CT、multipart 带 body）0 告警。
- 局限：只证明未初始化读，未取得稳定崩溃/信息泄露原语；修复版 Ubuntu 2.4.52 反汇编确认 `*rbuf=NULL/*size=0` 已存在且 0 告警。

**CVE-2022-23943（mod_sed 堆越界写）—— 未复现（资源受限，如实标注）**
- 修复点：`bufsize/size/remainbytes` 由 `int` 改 `apr_size_t`，`sz >= ctx->bufsize` 分支重排（2.4.52→2.4.53）。
- 可达性：需单条 sed 输出行 > `INT_MAX`（2GiB）；实测峰值 RSS ≈ 4.87× 行长（64MB→295,616kB；256MB→1,277,296kB），>2GiB 需 ~9–10GiB，本机 MemFree 仅 1.6–3.7GiB。
- 已完成：静态定位（`libsed wline(int sz)` → `sed_write_output(int sz)` → `memcpy(curoutbuf, buf, sz)`）+ 64/256MB 小规模验证 + 资源评估；未伪造命中。大内存机可 `CVE_23943_FORCE_FULL=1 bash poc/CVE-2022-23943/verify.sh`。
