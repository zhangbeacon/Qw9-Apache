# 01 · 项目方案

[返回首页](../README.md) · 下一篇：[漏洞矩阵](02-漏洞矩阵.md)

## 1. 要解决的问题

同一个攻击在同构部署上往往可重复成功。本项目要研究：**保持正常业务功能一致时，改变程序内部实现或运行结构，能否使同一攻击的结果发生可复核的改变？**

作品以 Apache httpd 2.4.49 为基准 V1。先建立漏洞与功能基线，再构造 V2/V3，最后用同一套输入比较三个版本。不能只用二进制哈希、地址或文件大小不同证明安全差异。

本页是整理后的方案摘要；旧版完整设计稿、赛题原文及选型过程保留在[历史归档](../archive/README.md)，不再作为当前进度表。

| 量化与交付 | 攻击成功率、迁移率、行为分布、性能和局限 | 未完成 |

## 3. 为什么选 Apache

已有选型记录支持 Apache httpd 2.4.49：网络接口明确、模块攻击面丰富，已有路径穿越、UDS SSRF、Lua 内存异常、请求/响应走私等实验基础。

选型已经结束，团队不应继续沿用旧笔记里的“先选 nginx/dnsmasq/Apache”任务。现阶段主要工作是**从漏洞基线走向变体与对比实验**。

## 4. 待实现的架构

```text
输入：固定 V1 源码 + 变体规格 + 功能契约 + PoC 与判定规则
                         ↓
执行层：构建 → 正常功能检查 → 固定 V2/V3 → 三版本实验 → 采证
                         ↓
判定层：机器断言、重复结果、负向对照、证据完整性检查
                         ↓
输出：构建溯源 + 功能差分 + 安全结果矩阵 + 量化报告

监管层（拟建，非可选）：LLM 值守构建、变换审查、测试、资源与采证，L1 白名单处置、L2 人审，无判定权
```

当前仓库提供的是 V1 的正式构建与验证脚本，不是已经实现上述整套流水线。模块边界、数据契约、门禁，以及"两项核心创新＋五项支撑机制"的完整设计，见[架构设计](architecture/README.md)。

### 变体构造候选

- 编译器、优化与加固组合、分配器等构建因素：作为候选实验变量，效果需要实测。
- 源码级语义等价重构：必须审查正常功能，并区分“改变利用条件”与“直接修复缺陷”。
- 配置变化：必须单独记录业务暴露面与功能契约，不能把关闭必要功能包装成免费安全收益。

不预先承诺某个 CVE 会在 V2/V3 失效，也不把 plain/ASAN 或 2.4.50/Ubuntu 修复版自动命名为 V2/V3。

## 5. 两项拟研究设计

### 执行、监管、裁决分离

确定性脚本执行任务，LLM 只协助诊断与提出处置建议；是否命中漏洞、是否保持功能一致，必须由机器判据与证据裁决。常驻监管服务及完整决策日志目前尚未实现。

### 行为分布与可复现性熵

拟重复测量“触发、静默、形态改变”的分布，研究跨变体稳定性。熵只描述结果分散程度，**不能单独等同安全增益**；高熵也不必然意味着更安全。还需同时报告攻击成功率、攻击目标是否达成、功能一致性及性能代价。

这仍是实验设计，当前没有跨 V2/V3 的熵结果或量化收益。

## 6. 实验纪律

1. 输入、版本、配置和判据固定后再比较；对每轮保存新鲜证据，不能沿用旧 PASS。
2. 区分漏洞仍存在但利用受抑制，与漏洞已修复；有限测试不证明绝对安全。
3. 同根因去重：CVE-2021-42013 与 CVE-2021-41773 不作为两个独立计分根因。
4. 版本对照要注明来源：现有负向对照是 Ubuntu 发行版回移补丁构建，不是全部 pristine 上游修复版。
5. 所有攻击实验只在隔离、明确授权的环境中执行。
