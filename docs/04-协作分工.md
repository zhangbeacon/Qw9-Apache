## 1. 四个人围绕同一条主线工作

以下是分工模板，不代表三个共创者已经被邀请或已认领。确认 GitHub 用户名后，将“待认领”替换为实际 owner。

| 角色 | Owner | 现在要做什么 | 可验收交付 |
|---|---|---|---|
| 负责人 / 架构 | 待确认 | 冻结 V2/V3 候选规格、正常功能契约与里程碑 | 版本、参数、种子、功能通过标准及设计审查 |
| 共创者 A / 漏洞根因 | 待认领 | 维护漏洞矩阵、核对独立根因、最终确认计分组合 | 每项判据、证据和局限，23943 不冒充动态成功 |
| 共创者 B / 构建验证 | 待认领 | 构建 V2/V3，做功能一致性与同 PoC 对比 | 新鲜日志、机器断言、重复测量和三版本矩阵 |
| 共创者 C / 工程文档 | 待认领 | 运行路径改造、统一调度、证据归档与交付整理 | 不误写原工作区的入口、完整退出码、链接与哈希校验 |

不再重新启动选型阶段，也不要每个人各写一份互相冲突的进度总览。

## 2. 当前从哪个分支开始

集成基线是 **`results-20261030`**；`main` 仍保留初始内容，尚未合并成果。

```bash
git clone --branch results-20261030 https://github.com/zhangbeacon/Qw9-Apache.git
cd Qw9-Apache
git switch -c feat/variant-build
# 完成一个明确任务后检查 diff、提交、推送自己的分支
```

发起 Pull Request 时，当前 **base 选择 `results-20261030`**。待负责人确认整合版本后，再单独决定是否合并至 `main`。不要强推覆盖别人，也不要直接把全部改动堆到共享分支。

## 3. 什么放哪里

| 内容 | 位置与规则 |
|---|---|
| 项目目标与设计取舍 | [项目方案](01-项目方案.md)，避免散落在多份草稿 |
| 某 CVE 当前结论或待办 | [唯一漏洞矩阵](02-漏洞矩阵.md)；需要细节再更新对应逐项报告 |
| 正式构建、配置与 PoC | [复现工程](../cve/apache/README.md)，保留明确的入口和依赖 |
| 新一轮证据 | 先保存至独立、本轮目录；审核后发布快照和精简索引，不直接 `git add` 几百份临时文件 |
| 一次性调试与旧方案 | 本地工作材料；确需保留时按[归档规则](../archive/README.md)固定版本、路径与哈希 |
| 密钥、登录信息、进程文件、缓存 | 不提交 |

Markdown 是协作设计源。生成的 Word/PDF 属于某一版交付物，不与正文平行手工维护两套状态。

## 4. 每个 PR 必须说清楚

1. **任务和范围**：解决哪个问题；是否改了正式入口、配置或运行路径。
2. **事实和计划分开**：哪些已运行，哪些只有静态检查，哪些仍是推演。
3. **验证记录**：运行环境、输入、退出码、证据位置；未测试就明确写未测试。
4. **状态同步**：结论变化只更新唯一漏洞矩阵，并给出对应证据。
5. **证据新鲜度**：不拿旧 PASS 冒充本轮，不删失败样本来制造全成功。
6. **审查与回滚**：至少一人审查；改动要可回退，不上传未经检查的敏感内容。

## 5. 本阶段的“完成”定义

不是又收集了一批资料，而是：**V2/V3 有真实构建、正常功能契约通过、同一输入在三个版本上的结果可重复且可解释，并有完整溯源。**

安全增益、性能和局限以实际数据报告；没有数据时，不用“已完成”“全自动”“绝对安全”等措辞。
