## 1. 研究链路

```text
官方发行包的 CHANGES 安全条目
    → 建立 CVE / 修复版本 / 源文件索引
    → 对修复前后版本做定点 diff
    → 阅读修复 hunk，提出触发条件
    → 与已有 PoC、负向对照及原始证据交叉核查
```

已有记录完成 11 个 CVE 的修复 hunk 定位。它证明进行了源码级分析，不等于所有漏洞都已动态触发，也不等于发现新漏洞。

## 3. 44790 定向 fuzz 证明了什么

历史记录围绕 multipart 边界与 `vlen = end - crlf - 8` 的关系进行定向变异。首轮采样时序可能使保存报文与真正崩溃的请求错位，因此必须逐个回放，而不能把“检测到过崩溃”直接记到当前保存样本上。

已保存的回放记录为：**60 个候选，8 个可单发回放，52 个回放失败**。失败样本和原始记录没有被删掉，完整保存在历史快照内。

结论只限于已知 CVE-2021-44790 的独立再发现与边界分析，**不是新漏洞、不是 60 个新崩溃，也不是变体安全增益实验**。

## 4. 为什么不直接沿用旧挖掘报告

[旧版挖掘报告](https://github.com/zhangbeacon/Qw9-Apache/blob/0fedb2552d888398e2152193e681bfe5b8f170b2/Apache项目/漏洞挖掘/漏洞挖掘报告.md)前部仍写“3 已复现 + 8 待验证”，后部又追加了新结果，并保留“v4 运行中”等当时状态。这适合追溯过程，不适合充当当前项目首页。

本次处理是保留原文及全部数据，另建立清晰的当前入口，不反向改写历史实验记录。源码下载、挖掘分析、回放和边界实验等旧工具都按原路径归档；它们没有被正式 PoC 自动调用。需要重做研究时，应在独立环境准备外部源码和工具，不能把解包理解为自动运行。
